## Evidence Recall 目前不能直接相信

```json
"evidenceRecall": 0.2903
```

这个 29% 是报告低分的主要原因，但目前存在实现缺陷。

Runner 接收到的 chunk 内容只有约 203 个字符，因为生成引用时执行了：

```ts
chunk.content.substring(0, 200)
```

因此即使 Agent 检索到了完整文档、生成了正确答案，Runner 也只能在前 200 字中搜索黄金证据。

例如 `procedure-002` 的答案完整列出了：

- 代码合并
- 预发验证
- 配置核对
- 依赖检查
- 通知

答案明显正确，但事件中保存的证据只截到文档开头，所以 5 个证据组全部被判为未召回。

类似的误判还有：

- `procedure-001`
- `procedure-002`
- `procedure-003`
- `procedure-004`
- `routing-edge-001`
- `context-001`
- `multihop-002`

共有 22 条样本因为 `evidenceRecall` 失败，10 条仅仅因为这一项而失败。

所以当前的：

```json
"evidenceRecall": 0.2903
```

更接近“前 200 字是否包含全部证据”，不是系统真实的证据召回率。

## 改写和实体检查过于严格

例如 `factual-002`：

黄金要求：

```text
补贴
差旅补贴
```

模型输出：

```text
补助
餐饮补助
```

答案正确回答了：

```text
100 元/天，无需发票
```

但仍然因为字符串不同而失败。

类似情况包括：

- “住宿”与“酒店”
- “补贴”与“补助”
- “常规窗口”与“常规生产发布”
- “发布前检查”与“生产发布”

因此：

```json
"rewrittenContains": 0.8064
"entityTermAny": 0.8709
```

包含不少同义表达导致的假失败。

## 禁止事实也有一次误判

`unanswerable-002` 的答案是：

```text
资料中未包含是否可以打到支付宝账户的信息
```

禁止事实是：

```text
可以打到支付宝
```

当前使用简单的字符串 `includes`，因此它在否定句中发现了“可以打到支付宝”，错误判定为违规。

这说明 `noForbiddenLiteral` 只能发现字面文本，不能理解：

- 否定
- 引用问题
- 假设
- 反驳

## 延迟偏高


也就是：

```text

问题分析耗时

```

## 一个更合理的临时解读

如果只忽略当前有明显误判的项目：

- `evidenceRecall`
- 严格的 `rewrittenContains`
- 严格的 `entityTermAny`
- 字面 `noForbiddenLiteral`

通过率约为：

```text
23 / 31 = 74.2%
```

如果只观察路由决策，通过率约为：

```text
26 / 31 = 83.9%
```

这两个是诊断性数据，不是正式成绩，但比 19.4% 更接近当前系统表现。

## 建议的修复顺序

第一优先级是修评估器：

1. 评估事件返回完整 chunk，不能截断到 200 字。
2. 将 `evidenceRecall` 拆成：
   - `evidenceGroupRecall`
   - `allEvidenceSuccessRate`
3. 无答案样本不强制召回黄金文档。
4. 改写和实体词支持同义词或语义判分。
5. 禁止事实改成否定感知或 LLM Judge。
6. 将意图改成可接受意图集合。

第二优先级才是修 Agent：

1. 排查精确词“某某科技有限公司”为何未召回。
2. 优化 `OA`、`SRE` 等词触发 keyword-only 后的召回下降。
3. 跨文档问题拆成多个子查询分别检索。
4. 同时用原问题和改写问题判断是否启用知识图谱。
5. 调整关键词检索阈值和长查询策略。

当前报告能够说明：系统运行稳定、路由总体不错，但关键词/跨文档召回存在真实短板；与此同时，评估器的证据截断和字面匹配造成了大量假失败。
